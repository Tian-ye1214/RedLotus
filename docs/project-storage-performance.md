# 项目存储性能结论

本报告整理 SQLite 记忆库候选与 LanceDB 的存储层证据。它不覆盖真实模型、embedding、rerank 或端到端 Agent 验收。

当前 SQLite 实现**未达到本次迁移门槛**：在公平的 100,000 条并发读写场景中，SQLite 的 P50 与 P95 查询延迟都高于 LanceDB。因此本轮不得将正式记忆库从 LanceDB 切换到 SQLite。

详细的脱敏统计在 [project-storage-performance.json](project-storage-performance.json)。原始报告的哈希列于该 JSON；测试材料按本轮清理清单删除，仓库不提交向量、正文、完整结果集或凭据。

## 复现条件

- 数据：1,000、10,000、100,000 条 1024 维向量；每档 64 个固定查询、top-k 30、随机种子 `20260917`。
- 机器：Windows 11 Pro 10.0.26200，Intel Core i9-13900HX（24 核 / 32 线程），约 31.8 GiB 内存。
- 依赖：Python 3.12.13、sqlite-vec 0.1.9、LanceDB 0.30.2、psutil 7.2.2。
- SQLite 候选：binary coarse vec0，候选数 240，full-float cosine 重排，`mmap_size=1 GiB`，chunk size 4096。
- 历史复现脚本：`sqlite_concurrency_acceptance.py`。SQLite 方案撤回后已按要求删除，脚本和原始证据的 SHA-256 保留在统计 JSON 中。

候选方案当时的 `memory_database.journal_mode` 为 `DELETE`；当前已删除 SQLite 配置并恢复 LanceDB。下面的 WAL 结果仅说明历史复制库上的诊断行为。

## 先前 query-only 对照

先前的同机 NTFS、五次重复对照全部通过。它使用等价的十列结果投影，并将 float32 向量物化为 Python 列表；三个规模的 SQLite 都在延迟、CPU、RSS、召回和结果载荷门槛上胜出。

| 记录数 | SQLite P50 / P95 | Lance P50 / P95 | 结果 |
| ---: | ---: | ---: | --- |
| 1,000 | 2.772 / 3.412 ms | 38.798 / 47.268 ms | 通过 |
| 10,000 | 4.297 / 5.279 ms | 43.899 / 53.211 ms | 通过 |
| 100,000 | 20.376 / 21.781 ms | 46.186 / 59.259 ms | 通过 |

这只能说明无并发写入时的查询表现；它不能证明正式记忆库在并发写入时满足迁移条件。

## 最终公平并发对照

最终对照改为与生产 RAG 一致的 `record_id`、`text`、`distance` 投影，不物化 embedding。两个后端均以同一个完整、不变的记录作为最多每秒一次的 upsert，五次重复；每个规模都在 600 秒内结束。饱和写入仅保留为原始诊断，未用于迁移门槛。

| 记录数 | 写入与读取真实重叠 | 结论 | 说明 |
| ---: | --- | --- | --- |
| 1,000 | 两端均重叠 | 通过 | 所有严格门槛通过。 |
| 10,000 | SQLite 未重叠 | 不接受 | 64 个查询过短，固定频率 SQLite 写入没有与读取重叠；该轮不形成跨库优劣结论。 |
| 100,000 | 两端均重叠 | 失败 | SQLite P50/P95 为 42.886/69.502 ms；Lance 为 30.889/34.957 ms。 |

100,000 条时 SQLite 的 CPU 为 2.406 秒、峰值 RSS 为 297,590,784 bytes，低于 Lance 的 5.797 秒和 668,667,904 bytes；SQLite 的每个查询召回也没有低于 Lance。但 P50 与 P95 都是本次硬门槛，两个延迟门槛失败，因此不能迁移。

## 100,000 条慢查询定位

对复制的 100,000 条 SQLite 候选库进行了五次、每次 64 查询的只读阶段分解。分解结果和单条 SQL 在语义上等价；一个距离并列的边界项选择了不同 ID，所以排序并非逐项一致，但距离序列相同。

| 阶段 | P50 | P95 |
| --- | ---: | ---: |
| vec0 候选查询 | 38.573 ms | 46.959 ms |
| payload 精排与结果投影 | 2.405 ms | 3.287 ms |
| 完整原查询 | 40.017 ms | 46.126 ms |

候选查询执行计划是虚拟表扫描和 `ORDER BY` 的临时 B-tree。payload 表确实有 100,000 个 overflow 页，但精排和投影只占分解 P50 的 5.75%，并非主耗时。因此没有尝试 page-size 或 VACUUM 参数组合，也没有在缺乏证据时修改查询语义或召回条件。

## E 盘 WAL 诊断

在 E 盘复制库上执行三次短写/读并发和一次受控未提交写入中断：每次写入与读取重叠，结果 ID 和召回保持不变；中断后 sentinel 记录为零、`integrity_check=ok`、两张表各 1,000 条、可以取得并释放独占锁。重开后 WAL/SHM 边车文件消失。

这说明 WAL 在该复制库上能够完成所测恢复流程，但不抵消 100,000 条公平并发的延迟失败。

## 后续约束

- 保留 LanceDB 作为本次正式记忆库后端。
- 不把 query-only 的通过结果或 E 盘 WAL 诊断描述为迁移通过。
- 任何新的 SQLite 候选必须重新满足同机、同数据、同投影、真实写读重叠的全量门槛，才可重新评估。
