## 当前结论

**尚未通过验收，未合并。** 正式 `develop` 和正式记忆仍使用 LanceDB；未迁移正式记录，未修改全局配置。开发分支已经实现 SQLite 向量存储，但不能据此宣称正式替换完成。

最终公平并发对照中，十万条向量的 SQLite 查询 P50/P95 为 42.886/69.502 ms，LanceDB 为 30.889/34.957 ms。SQLite 的 CPU 和内存较低、召回未降低，但延迟不满足“各档均优于 LanceDB”的门槛。一万条的该批查询没有与写入实际重叠，亦不能算并发通过。只读查询曾通过，不替代并发结论。WAL 为诊断配置，应用配置仍为 DELETE。

## 本轮发现并修复的问题

| 问题 | 原因 | 修复与证据 |
|---|---|---|
| 新进程加载图片会话失败 | 引用恢复使用进程当前目录，没有传递所属项目 | 会话对象保存显式 workspace，预检、加载和证据解码统一传递；真实第 19 回合现场零请求加载成功，ID/计数不变 |
| 后台日志写入其他项目 | 全局日志目录与旧任务上下文交错 | 日志按当前执行 workspace 路由；会话与任务上下文保留其来源，旧项目上下文不能覆盖新项目 |
| 深路径 SQLite 可打开却不能写事务 | journal 文件后缀触及 Windows 路径边界 | 使用同一文件的标准扩展路径拼写，不改存储盘或回退目录；真实写入回归通过 |
| 旧索引任务覆盖纠正后的正文向量 | embedding 前后没有再次确认正文版本 | 网络调用在事务外；提交时在事务中重查 hash/有效状态，向量和索引戳一同提交 |
| 跨项目/全局范围纠正留下旧记录 | 两个数据库各自提交，旧范围仍 active | 同一短事务协调正式记录更新；旧范围保留 superseded 墓碑及显式纠正优先级 |
| 复制进来的其他项目会话可能被空间清理删除 | 新目录布局下只校验会话 ID | 清理同时核验当前项目 ID；归属不符保留 |
| 项目 A 的控制操作清理项目 B | 初始化、压缩等控制路径的持久化未绑定指定项目，空间清理沿用进程当前项目 | `_durable_write` 明确绑定 self.workspace 并传递到线程；真实隔离 A/B ENOSPC 回归先复现删除 B，再验证只清理 A、保留 B 并恢复调用方上下文 |
| 多 ID 清理可能超过 SQL 参数数 | 每条 ID 占用一个绑定参数 | JSON 参数展开 ID 集合，实际低变量限额回归通过 |
