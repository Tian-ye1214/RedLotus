# ZipVoice 接入约定与开发计划

本文规定下一阶段的部署接口和验收顺序。当前正式链路仍为 X-ASR 与 Kokoro；Markdown 朗读解析独立于模型。ZipVoice 尚未接入应用安装清单，也没有取得本项目的真实音色、性能及长稳验收结果。

## 制作端与 RedLotus 的边界

制作端独立接收专用参考音频与逐字对应的文本，检查单说话人、噪声、截断、采样率和文本一致性；必要时在独立 GPU/PyTorch 环境微调、蒸馏、导出和量化。训练数据、训练脚本、优化器状态及 `.pt`/`.pth`/`.ckpt` 不进入 RedLotus 的运行依赖。RedLotus 不提供训练入口，也不在首次加载时执行转换或训练脚本。

提供一段音频和文本，首先对应 ZipVoice 的参考条件克隆；标准运行路径仍需要这两项资料，不能将其称为已经永久固化音色的专属权重。共享基础权重可搭配多个显式制作的音色资料。需要微调时，制作端交付新的基础模型身份；不同基础模型不混用参考条件缓存。

运行统一使用 sherpa-onnx CPU。先以官方 ZipVoice-Distill 中英模型建立基线，再按效果决定是否在制作端微调／蒸馏。普通 ZipVoice 微调产物使用其验证过的步数，不能直接套用蒸馏版四步推理；INT8、FP32 分别听评和测量，不假设量化一定更快或不损失音质。

依据：[官方部署说明](https://k2-fsa.github.io/sherpa/onnx/tts/zipvoice.html)、[微调流程](https://github.com/k2-fsa/ZipVoice/blob/master/egs/zipvoice/run_finetune.sh)、[ONNX 导出](https://github.com/k2-fsa/ZipVoice/blob/master/zipvoice/bin/onnx_export.py)。

## 固定部署资源

在现有全局 `~/.redlotus/model` 及版本管理下，模型实现接收已经校验的版本目录。该目录中采用以下固定相对名称，不扫描任意 ONNX 文件推测用途：

| 相对名称 | 用途 |
| --- | --- |
| `encoder.onnx` | 文本编码器；制作端将对应 FP32 或 INT8 产物统一命名 |
| `decoder.onnx` | 与基础版本匹配的生成网络 |
| `vocoder.onnx` | 匹配 24 kHz 输出的 Vocos 声码器 |
| `tokens.txt`、`lexicon.txt`、`espeak-ng-data/` | 与上述模型匹配的文本前端资源 |
| `model.json` | 被动部署元数据及每个资源的 SHA256、字节数 |
| `voices/<voice_id>/reference.wav` | 明确导入的专用参考声音 |
| `voices/<voice_id>/reference.txt` | 与参考声音逐字一致的 UTF-8 文本 |

`model.json` 的 schema 固定版本；必要字段为后端 `zipvoice`、基础模型版本、变体 `zipvoice` 或 `zipvoice-distill`、输出采样率 `24000`、已验证推理步数及资源校验清单。它不允许 Python 模块名、可执行脚本、自定义动态库、外部 URL 或越出版本目录的资源路径。文件名一致不代表兼容：加载器还须校验图输入输出、采样率、词表与变体元数据。

应用只读取已经制作好的资源。部署说明和本地显式导入不赋予未知来源权重自动可信身份；只有用户明确选定的本地资源或应用固定发布清单可成为候选。校验后沿用现有版本登记、占用锁、回滚与清理规则。升级到新版本目录，不覆盖正在被原生运行时引用的文件；后端／权重变更在下次启动生效。

专用参考声音是允许持久保存的用户音色资料，不属于日常录音或中间缓存。读取、解码和重采样到内存均在工作线程完成，进入原生推理时传递参考 PCM 与文本，不复制生成第二份文件。日常录音、合成 PCM、渠道音频与待播正文始终不落盘；模型清理不能删除用户原始音色资料。

## 类型化接口与职责

现有 `SpeechModel`、`ASRModel`、`TTSModel` 继续作为模型契约。下一阶段迁移所有调用方，不保留裸整数音色参数的转发兼容层。

| 类型／方法 | 唯一职责 |
| --- | --- |
| `ModelBackend` | 枚举 X-ASR、Kokoro、ZipVoice；与表示 ASR/TTS 能力的 `ModelKind` 分开 |
| `SpeechModel.load / warmup / close` | 构造、预热、释放单个原生模型，不下载、不训练 |
| `ASRModel.create_session` | 创建独立识别状态；识别会话负责接收 PCM、收尾和关闭 |
| `VoiceProfile` | 不可变的音色身份、兼容基础模型身份和资源描述 |
| `TTSModel.prepare_voice(profile)` | 生成该模型使用的类型化 `VoiceCondition`，检查兼容性 |
| `SynthesisRequest` | 已清理的纯文本和本次调用固定的音色条件 |
| `TTSModel.generate(request, callback)` | 合成一个有界文本片段，返回或回调 PCM |
| `ModelFactory.create_asr / create_tts` | 按枚举构造已支持的实现，返回明确的 ASRModel/TTSModel 类型 |
| `SpeechService` | 共享实例、后台准备、限流、取消及回收 |

`KokoroVoiceCondition` 保存中文／英文音色选择；`ZipVoiceCondition` 保存专用参考 PCM、匹配文本与已验证参数。状态属于一次合成响应，不能把上一会话的语言或参考声音放进共享模型可变字段。Kokoro 的英文数字前处理归 Kokoro 实现；公共 Markdown 解析器与分句器不判断模型音色，也不为每个说话人建立子类。

一个响应固定一个 `VoiceProfile`；同一基础模型的音色切换在新回合生效。全进程仍只驻留一套 ASR 和当前选定的一套 TTS，不因拥有多个音色资料加载多个基础模型。原生调用结束之前，取消不能释放模型名额、换权重或创建替代实例。

四个公共能力继续是类接口：`parse_input`、`recognize`、`synthesize`、`parse_output`。ASR 输入为 16 kHz 单声道 float32；TTS 对外输出为 24 kHz 单声道 float32，原生输出率不同则通过音频层真实重采样。ZipVoice 初版按片段合成后连续播放；不能把分块搬运称为模型逐帧生成。

## 实施顺序与交付门槛

1. 完成当前 Markdown 解析及 Kokoro 回归、真实扬声器试听；与真实终端中 Agent 回复的验证分别记录。
2. 在制作端准备一个明确授权使用的参考音色，交付固定文件与元数据；在没有 PyTorch 的运行环境检查完整推理依赖。先验证官方蒸馏模型，避免将普通微调、蒸馏和运行优化混成一次结果。
3. 增加类型化请求与音色条件，把 Kokoro 的语言和数字处理移入模型实现，再按同一契约实现 ZipVoice；工厂、服务与所有调用方一次迁移。保持 TTS 五文件、每文件最多 500 行有效代码，业务逻辑不转移到测试脚本。
4. 扩展现有模型目录／版本登记，校验固定文件、图接口与音色身份。缺失、损坏、变体不匹配、加载失败时只停用语音并给出简短原因；全链路下载、读取、校验、加载和预热仍在线程中执行。
5. 使用至少 20 条中英文、混合语言、数字、术语及长句验收；固定句重复十次，核对音色一致性、漏读、重复、可懂度和中英切换。参考文本不匹配、近乎静音或多说话人的资料必须能给出明确诊断；输入质量不足时不能承诺任意单段音频都可稳定克隆。
6. 先人工试听，再记录 ASR 共存时的首块 PCM、实际首声、RTF、内存、线程与句柄；比较 FP32/INT8，覆盖连续生成、取消及跨会话隔离。原有 P95 首块 ≤1 秒、RTF <1、约 1 GiB 常驻增量仍是目标，未实测不得写成已达标。
7. 在源码、安装 wheel、onedir、onefile 中实际推理与播放，随后单独完成新版本 24 小时资源测试。真实账号与真实设备验收不能由模拟、ASR 回转写或旧版本记录替代。

测试过程不导出 WAV、MP3 或待播文件；只记录文字、版本、校验值、耗时及资源指标。已明确导入的参考资料不受此限制。未经上述验收不改变默认 TTS，不发布声称支持稳定克隆的制品。
